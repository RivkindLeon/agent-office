# Developer — критерии приёмки работы

Работу принимают по каждому пункту ответом «да» или «нет».

1. Изменение реализует ровно одно поведение из выданной задачи `tasks.json`, связано с её требованием `REQ-…` и не добавляет требований сверх входного брифа.
2. До появления реализации существует красный тест на это поведение, а событие `test_red` с выводом прогона записано в журнале; зелёная фаза выполнена в следующую смену.
3. После реализации тест проходит, событие `test_green` с выводом прогона записано в журнале, и текущая задача имеет статус `green`.
4. Для каждого входа, который задача обязана обрабатывать, зафиксирован явный результат; неизвестный вход, если он может быть передан, завершается ошибкой, а не `undefined`.
5. В изменении нет мёртвых веток или молчаливых значений по умолчанию; при наличии вариантов поведения их обработка не требует отдельной ветки для каждого варианта.
6. Head of Engineering подтверждает по `org/PATTERN-CODE-REVIEW.md`, что изменение является одним самодостаточным блоком ориентировочно стандартного размера и что вариации одного поведения не раздроблены на отдельные задачи.
7. `REVIEW-REQUEST.md` передан Head of Engineering и содержит изменённые пути, доказательства прогонов и сведения о незакрытых вопросах; разработчик не объявляет собственную работу принятой.
